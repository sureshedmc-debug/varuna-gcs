# Idea batch — 2026-10-07

Read against the pipeline as it stands today: `src/lib/detector.js`,
`src/lib/track.js`, `src/lib/feedbackLearner.js`, `src/lib/sizeEstimate.js`,
`src/components/WebcamDetect.jsx` (the detect loop, ~line 444).

## Where the accuracy actually goes

`public/models/plastic.json` reports the honest numbers for the shipped model:

| class | precision | recall | mAP50 |
| --- | --- | --- | --- |
| plastic bottle | 0.46 | 0.54 | 0.53 |
| plastic bag | 0.31 | 0.39 | 0.32 |
| plastic cup | 0.27 | 0.45 | 0.33 |
| plastic container | 0.17 | 0.29 | 0.12 |
| other plastic | 0.32 | 0.35 | 0.27 |

Two things follow, and they shape most of this batch.

**Precision is the bottleneck, not recall.** At the recommended 0.223
confidence, roughly two out of three boxes are wrong for every class except
bottles. The operator sees a busy screen and learns to distrust it. Every
counted false positive also lands in `trashLog` and skews the hotspot map and
the report.

**One global threshold is wrong by a factor of three.** The loop uses a single
`confRef.current` for all six classes (`WebcamDetect.jsx:451`), but a container
at 0.3 is near-worthless while a bottle at 0.3 is a fair bet.

The good news: this is a *video* pipeline with a human in the loop, and it is
currently throwing both of those advantages away. Ideas 1, 4 and 8 are all
"use the time axis"; 2, 7 and 9 are "stop discarding evidence you already have".

---

## Do these first

1. **Confirmation-gated counting** (#1) — the single biggest precision win
   available, no new model, ~40 lines.
2. **Per-class thresholds** (#2) — ~20 lines, data already sits in the sidecar
   JSON.
3. **Replay eval harness** (#11) — without it you cannot prove any of the rest
   worked, which is why the v2 model shipped with `recommended_conf` set to a
   library default and no metrics at all.

---

## 1. Confirmation-gated counting (temporal voting in the tracker)

`BoxTracker.update()` overwrites the score every tick — `t.score = b.score`
(`src/lib/track.js:53`) — so a box that appeared once at 0.31 is treated
exactly like one seen for two straight seconds at 0.31. A flicker and a real
bottle are indistinguishable to everything downstream.

Keep per-track history instead:

```js
t.hits++                                   // frames this track was matched
t.scoreSum += b.score                      // → mean score over its life
t.peak = Math.max(t.peak, b.score)
t.misses = 0                               // reset on every match
```

Then gate on it. A track becomes *counted* only once
`hits >= 3 && mean >= conf`, and once promoted it stays promoted through short
occlusions (that is what `maxAgeMs` already buys). Report `mean` as the
on-screen confidence, not the latest frame's — it is a far better estimate.

Why this is the big one: flicker false positives are *uncorrelated* across
frames, real objects are *correlated*. Requiring 3-of-N confirmations squares
(roughly cubes) the suppression of the former while leaving the latter
untouched. That is the T-CNN / tubelet result, applied with no extra
inference. It also unlocks something better — because precision is now
recovered temporally, you can *lower* the per-frame threshold toward 0.15 and
pick up genuine recall you are currently discarding. Precision and recall both
improve, which almost never happens from one change.

Second-order win: promote on evidence, demote on absence. Give each track a
small decaying score so an object that stops being re-detected fades out of the
count rather than vanishing, which is also what stops the count number
twitching on screen.

Cost: ~40 lines in `track.js`, plus reading `hits`/`mean` where the loop builds
`counted` (`WebcamDetect.jsx:517`). No model change, no extra compute.

## 2. Per-class confidence thresholds from the model's own metrics

`plastic.json` already carries per-class precision and recall. Derive a
threshold per class instead of one global number — pick for each class the
confidence where precision crosses a target you choose (say 0.6), and store it
in the sidecar as `per_class_conf`:

```json
"per_class_conf": { "plastic bottle": 0.20, "plastic bag": 0.35,
                    "plastic cup": 0.38, "plastic container": 0.55,
                    "other plastic": 0.40 }
```

Then in `createPlasticDetector`'s filter (`detector.js:~195`), drop boxes below
their own class's floor. Keep the global slider as a *bias* applied on top, so
the operator's control still works.

This needs one evaluation pass in Colab to read the thresholds off the PR
curves — you already have the test split, so it is a notebook cell, not a
retrain. It is the cheapest honest precision improvement in this list, and it
makes the weak classes stop polluting the count without blinding you to them.

While you are there: `plastic_detection.json` (the v2 test model) ships with
`"recommended_conf": 0.25` and the note "no evaluation metrics were supplied".
An unevaluated model cannot be compared against the default one — see #11.

## 3. Geo water-body mask as a detection gate

`src/lib/waterBody.js` already fetches real water polygons from OSM, and
`@turf/boolean-point-in-polygon` is already a dependency used for mission
planning. Nothing in the detection path uses either.

When a mission's water polygon is known, project each detection's box centre to
a world coordinate (you have drone lat/lng, altitude and FOV in
`sizeEstimate.js`) and gate on `booleanPointInPolygon`. Anything on the bank,
the road, the parked scooters, the crowd watching the demo — gone, for free, by
construction.

Keep it a *soft* gate at first: tag out-of-water boxes rather than deleting
them, feed "distance to water edge" as a feature to the learner (#5), and let
the operator watch it for a flight before you trust it. GPS error and oblique
camera angles mean the mask is ±5 m, so a hard gate would quietly eat real
detections along the shoreline, which is exactly where river litter collects.

This one is a genuine differentiator — a detector that knows what water *is*
is a different class of product from one that just scores boxes.

## 4. Drift coherence — real debris moves with the current

A floating bottle and a ripple glint look similar in one frame. Over two
seconds they do not: the bottle translates smoothly and *in the same direction
as every other floating object in the scene*, while glint flickers in place and
ripples move with the wind.

With #1 in place each track already has a position history. Compute two numbers
per track:

- **self-coherence** — the ratio of net displacement to total path length.
  Near 1 for drifting debris, near 0 for something jittering in place.
- **scene agreement** — the cosine between this track's drift vector and the
  median drift of all tracks in the frame.

Subtract the camera's own motion first (the drone is moving too): the median
displacement of *all* tracks is a decent free proxy for ego-motion, so the
residual is the object's own drift.

Both become features for the learner. This is the kind of signal no
single-frame detector can access and no amount of retraining will give you, and
it is the one that will hold up on real river footage with chop and sun on the
water.

## 5. Glint and blown-highlight features

`describePixels` (`feedbackLearner.js:~70`) computes brightness, contrast and
saturation. Sun glint has a specific signature it does not capture: pixels
clipped at the top of the range, achromatic, with a hard edge.

`EXTRA_FEATURES` is 8; make it 11 and add:

- **clipped fraction** — share of pixels with max channel ≥ 0.98.
- **achromatic-bright fraction** — share with saturation < 0.1 *and* value > 0.9.
- **edge-contact-with-water** — distance from the box to the nearest frame
  region that looks like water (or, with #3, to the water polygon edge).

The learner then discovers "bright, colourless, clipped, in open water" = glint
from a handful of operator ✖ answers, rather than needing one answer per glint.
Cheap: the pixels are already being walked, the loop just accumulates three
more counters.

Note the migration: changing `featureDim` invalidates the stored posterior
(`varuna.rl.v2`). Bump the key to `v3` and let it relearn, or pad old weight
vectors with zeros — do not silently reinterpret the old ones.

## 6. Saliency-priority tiling instead of round-robin

The long-range pass walks tiles in fixed order — `tileIndexRef.current % tiles.length`
(`WebcamDetect.jsx:~468`). On a 3×3 grid every tile gets 1/9 of the zoom
budget, including the 6 that are empty sky, empty water, or the same patch of
bank for the whole flight.

Score each tile and always scan the best one:

```
priority = recentDetections * 2 + pixelVariance + timeSinceLastVisit * decay
```

Variance is nearly free from the letterbox canvas you already draw. The
`timeSinceLastVisit` term is what keeps it honest — it guarantees every tile is
eventually revisited, so you cannot get stuck staring at one hotspot while
debris drifts in unwatched.

This is the adaptive-slicing result ([Adaptive SAHI, 2026](https://tldr.takara.ai/p/2604.19233))
reached cheaply: same compute, materially better small-object recall, because
the zoom budget lands where objects actually are. Plain SAHI slicing buys
+5–7 AP on aerial benchmarks ([Akyon et al.](https://ar5iv.arxiv.org/html/2202.06934));
you already have the slicing, you are just spending it uniformly.

## 7. Soften person suppression

`suppressByPerson` removes **any** trash box overlapping **any** person box by
**any** amount, and the comment says so in capitals
(`detector.js:355`). On a river with people on the bank or in boats, that
deletes real floating litter whose box happens to clip a distant person.

Use containment instead: suppress only when ≥ 0.6 of the trash box lies inside
the person box (`overlapRatio` already computes exactly this), or when the
trash box is small and sits in the person's upper-body region — a bottle in
someone's hand is the case you actually want gone.

Keep the aggressive mode behind the existing human-detection toggle for demos
where a person walking through frame must never produce a box, but make
containment the default for flight.

## 8. Free test-time augmentation via letterbox jitter

`preprocess` centres the letterbox padding deterministically —
`padX = floor((inputSize - nw) / 2)` (`detector.js:~230`). Every frame
therefore lands on the same pixel grid, and an object that falls badly against
that grid is mis-detected *consistently*, frame after frame. Temporal voting
(#1) cannot save it, because the error is correlated.

Jitter the pad by a few pixels per frame (cycle through, say, ±0, ±3, ±6). Each
frame then samples a slightly different grid alignment, and #1's vote across
frames becomes a genuine multi-crop ensemble — the accuracy of TTA at exactly
zero extra inference cost, because you were going to run that frame anyway.

Only works in combination with #1. Do them together.

## 9. Class-aware Soft-NMS for debris rafts

`nms()` (`detector.js:~370`) is class-agnostic and hard: of two boxes with IoU
above the threshold, the lower-scoring one is deleted outright, even if it is a
different class. River litter arrives in *rafts* — bottles wedged against bags
against foam — so neighbouring true positives routinely sit above 0.4 IoU and
get erased.

Two changes, both small:

- Only suppress within the same class (or within a small confusable set —
  bottle/container/cup genuinely do compete).
- Soft-NMS: decay the overlapping box's score by `exp(-IoU²/σ)` instead of
  zeroing it, and let the threshold decide afterwards.

Expect a visible recall gain precisely in the dense-debris frames that matter
most for the report, since those are where the item count drives the headline
number.

## 10. World-frame track dedupe

The loop geotags at most twice a second (`lastGeoTagRef`, `WebcamDetect.jsx:~522`)
and `trashLog` merges sightings within 5 m (`trashLog.js:25`). Hover over one
bottle for ten seconds and it is recorded ~20 times, merged by *location*, so
the count depends on how long the drone loitered rather than on how much litter
there is.

Project each **track** (not each frame's boxes) to a world coordinate and
record it once, on track *retirement*, with its best frame as evidence. The
maths is already in `pixelBoxToRealSize` — you need the inverse: box centre →
ground offset → lat/lng via drone position and heading.

This changes the reported totals, probably downward and substantially. That is
the point: right now the headline number is not defensible, and a judge or an
official who asks "how do you know that's 340 bottles and not the same 40
counted eight times" has no answer. After this, it does.

Pairs naturally with #3 — the same box-centre-to-world projection serves both.

## 11. Replay-based offline eval harness and model A/B

`missionRecording.js` already captures every detection run as a `.webm` clip.
`ReplayScreen.jsx` never runs the detector over them.

Build the loop you are missing: load a clip, step it frame by frame through
*both* models, and show the diff — counts, per-class, agreement rate, and the
frames where they disagree most. Add a small "truth set" of operator-labelled
frames (you already save them in IndexedDB with every ✔/✖) and it reports real
precision and recall per model.

This is unglamorous and it is the highest-leverage thing in the whole list,
because it converts every other idea here from a guess into a measurement. It
is also why `plastic_detection.json` currently says "no evaluation metrics were
supplied" — there was no way to produce them without a GPU and a Colab session.
After this, re-evaluating a candidate model is dragging a file onto a screen.

Run it in a Web Worker against an `OffscreenCanvas` so the UI stays alive, and
let it go faster than real time (there is no need to honour frame timing when
nobody is watching).

## 12. Hard-negative-first dataset export

The learner keeps up to 2000 examples with frames (`MAX_SAVED`,
`feedbackLearner.js:52`) and can export them for a retrain. But a retrain
learns most from the examples the current model got *most wrong*, and the
export treats all 2000 equally.

Rank them before export: highest detector confidence among ✖ answers (confident
false positives), lowest among ✔ (missed true positives), and the ones where
the learner and the detector disagreed most. Export the top N with that order
preserved, and write the ranking into the dataset manifest so the training
notebook can oversample them.

Standard active learning, and it compounds: each retrain gets the operator's
scarcest resource — their attention — spent where it buys the most.

## Out of the box

These are the ones that make the project read as a product rather than a
well-built demo.

## 13. Open-vocabulary classes the operator types in

Today the class list is frozen at the six in `plastic.json`. Retraining to add
"thermocol sheet" or "fishing net" or "water hyacinth" is a Colab session.

An open-vocabulary detector — YOLO-World or YOLOE — scores boxes against *text
embeddings* instead of a fixed head ([YOLO-World, CVPR 2024](https://arxiv.org/abs/2401.17270)),
and it is CNN-based, roughly 20× faster and 5× smaller than Grounding DINO, so
it is in the right weight class for this app.

The trick that makes it work in a browser: **you do not need the text encoder
at runtime.** Pre-compute the embedding for each phrase offline, ship them as a
small JSON table beside the ONNX file, and the operator "adds a class" by
picking a phrase whose vector you already have. Ship 50 phrases covering Indian
river litter — thermocol, fishing net, cloth, coconut shell, idol remains,
flower offerings, oil sheen, hyacinth mat — and the app detects things the
TACO-trained model has never seen, with no retrain and no API key.

That is a demo that answers "what if we point it at a different river", which
is the first question anyone serious will ask.

Fallback if an ONNX export proves awkward: your `feedbackLearner`
fingerprints are already a crude embedding space. Let the operator name a
cluster of ✔ answers and you have operator-defined classes without any new
model at all. Less impressive, far less work, same demo beat.

## 14. On-device VLM second opinion and offline evidence captions

`SmolVLM 256M` runs entirely in a browser on WebGPU via Transformers.js at
usable speed ([HF](https://huggingface.co/blog/smolervlm)) — the same WebGPU
path `detector.js` already sets up and already knows how to fall back from.

Two uses, both of which the project currently cannot do offline:

- **Adjudicate the uncertain boxes.** For each box the learner marks `explore`,
  crop it and ask "is this plastic litter floating on water?" You get a second
  opinion from a model with completely different failure modes than a YOLO
  head, on exactly the boxes where a second opinion is worth having. Budget it
  — a handful of crops per second, not every box.
- **Caption the evidence.** Every geotagged sighting in the report gets a
  one-line description of what is actually in the photo. The report stops being
  a table of coordinates and becomes something a municipal officer reads.

The decisive part: `llmProviders.js` gives the operator Groq, Gemini,
OpenRouter and custom endpoints — all of which need an API key and a working
uplink. On a riverbank over Netbird with one bar of signal, none of them exist.
A 256M model in the page does. "The AI still works with no internet" is a
sharper claim than any provider list.

## 15. Upstream source attribution

`clusterHotspots` ranks *where* litter is. Nobody can act on that alone — they
want to know *where it comes from*.

You have everything needed: hotspot positions over time, the river's flow
direction (OSM waterway geometry, already fetched in `waterBody.js`), and
timestamps. Litter found at a hotspot entered the water upstream. Walk the
waterway geometry upstream from each hotspot, weight by how fast debris
plausibly drifts, and mark the stretch where the mass most likely entered —
then overlay the drains, bridges and settlements OSM already knows about along
that stretch.

Output: "68% of the plastic logged this week is consistent with entry between
the Ambedkar bridge and the Nala outfall, 1.2 km upstream." That is a sentence
that changes someone's budget. Every other river-drone project reports what it
picked up; this one would report who to go talk to.

Be careful to present it as a hypothesis with its assumptions visible — flow
speed, time window, confidence — rather than a verdict. The credibility of the
whole report rests on not overclaiming here.
