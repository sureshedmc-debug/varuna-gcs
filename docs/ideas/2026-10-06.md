# 2026-10-06 — Varuna AI: detection & product ideas

**What I read today:** `src/lib/detector.js`, `src/components/WebcamDetect.jsx`
(the live loop, lines 429–540), `src/lib/track.js`, `src/lib/feedbackLearner.js`,
`src/lib/labels.js`, `src/lib/sizeEstimate.js`, `src/lib/cocoRunner.js`,
`src/lib/personDetector.js`, `src/lib/trashLog.js`, `public/models/plastic.json`.

**The one-line diagnosis.** The engineering around the model is strong — shared
reference-counted ONNX sessions, WebGPU-with-CPU-fallback guards, SAHI-style
tile scanning, an IoU tracker, a self-learning operator filter. The *model
itself* is the bottleneck: `public/models/plastic.json` reports **mAP50 0.2933**
overall, and **0.12 for `plastic container`**. No amount of UI work moves that.
Everything in Tier 1 below is about closing that gap without retraining from
scratch.

---

## Tier 1 — do these first (highest gain per hour)

### 1. [ACCURACY] Fine-tune on aerial *water-surface* data, not ground litter
**Effort: 6–10 h (mostly Colab waiting) · Expected gain: the single biggest available — plausibly mAP50 0.29 → 0.5+ on real river footage**

`public/models/NOTICE.txt` says plastic.onnx was trained on **TACO** — which is
hand-held photos of litter *on the ground*, shot from 1–2 m. Varuna flies over
*water*, looking down, through sun glint, ripples and wake. That is a textbook
domain gap, and it explains a 0.29 mAP far better than any architecture choice.

Two datasets published since that training run match Varuna's domain almost
exactly:

- **AquaPlasticWaste 2026** — 5,000 UAV images of floating plastic on Dal Lake,
  Kashmir. COCO JSON *and* YOLO polygon/segmentation labels. Crucially, its
  stated statistics mirror Varuna's problem: mean plastic coverage **1.40 % of
  pixels**, median instance **1,448 px²** — far smaller than COCO-scale objects.
  Indian inland water, which also makes it the right dataset to *cite* in a
  report or grant application.
- **RFT (River Floating Trash)** — 2,400 high-res images, rivers and lakes,
  sunny *and* cloudy, nearshore *and* drone-aerial, boxes + polygons.

**Do:** keep the current 6-class head, fine-tune the existing yolo11s weights on
TACO + AquaPlasticWaste + RFT combined (not AquaPlasticWaste alone — TACO keeps
the close-range webcam demo working). Re-export to ONNX at 640, regenerate
`plastic.json` from the new validation run. **No app code changes** — the sidecar
contract in `createPlasticDetector()` (`src/lib/detector.js:161`) already makes
the model a drop-in swap. That design decision pays off here; use it.

**Watch for:** AquaPlasticWaste is segmentation-labelled; convert polygons to
boxes for the detection head, or keep the polygons and consider idea #9.

### 2. [ACCURACY][BUG] Aggregate confidence over a *track*, not a frame
**Effort: 3–4 h · Expected gain: literature on this reports 40–60 % fewer false positives at equal recall**

Right now `BoxTracker.update()` (`src/lib/track.js:53`) smooths box *geometry*
across frames but **overwrites the score** with the newest observation
(`t.score = b.score`), and `WebcamDetect` counts a box the first frame it
appears. So a single-frame flicker at 0.21 confidence counts, logs a sighting,
and can fire a big-dump email — while a genuine bottle that dips to 0.19 for one
frame disappears from the count.

Video gives you a free, powerful signal the current code throws away: an object
seen in 5 of the last 6 frames is real; one seen once is noise. This is the
standard fix (Seq-NMS, tubelet aggregation, tentative tracks in ByteTrack).

**Do, inside `BoxTracker`:**
- Add `hits`, `misses`, and `scoreEma` to each track.
- `scoreEma = scoreEma*0.7 + newScore*0.3`; expose it as the box's score.
- Add a `confirmed` flag: `hits >= 3` *or* `scoreEma >= 0.5`. Emit `confirmed`
  on the returned boxes.
- In `WebcamDetect.jsx:502`, count and log **only confirmed** tracks; draw
  unconfirmed ones faintly (the UI already has a dashed "explore" style from the
  learner — reuse it).

**The payoff compounds:** once counting requires temporal confirmation, you can
safely *lower* `DETECT_CONF_FLOOR` (`WebcamDetect.jsx:87`) from 0.2 to ~0.12 and
recover the small, distant objects the model currently finds at 0.15 and
discards — recall up *and* false positives down, which single-frame thresholding
can never give you at the same time.

### 3. [SPEED] Turn on multi-threaded WASM — you are leaving 2–4× on the table
**Effort: 2–3 h · Expected gain: 2–4× CPU inference on any machine without a usable GPU**

`src/lib/detector.js:15` pins `ort.env.wasm.numThreads = 1`. ONNX Runtime Web
enables threads by default and they are a large win — but **only when
`crossOriginIsolated` is true**, which needs two response headers. Pinning to 1
is the correct *defensive* choice while those headers are absent; the fix is to
send them, not to keep one thread.

This matters more for Varuna than for a typical web app, because the WebGPU path
is explicitly abandoned for the whole session after one failure
(`webgpuFailed`, `detector.js:39`) — exactly the situation on a field laptop
with a blocklisted driver. The single-threaded WASM path *is* the field path.

**Do:**
- `electron/server.cjs` (the headers block around line 129): add
  `Cross-Origin-Opener-Policy: same-origin` and
  `Cross-Origin-Embedder-Policy: credentialless`.
- `vite.config.js`: same two under `server.headers` and `preview.headers`.
- `detector.js:15`: `ort.env.wasm.numThreads = globalThis.crossOriginIsolated ? Math.min(4, navigator.hardwareConcurrency || 1) : 1`
  — keeps the safe behaviour anywhere the headers don't land.

**Test before trusting it:** use `credentialless`, not `require-corp` — the Pi's
MJPEG `<img>` and the OSM map tiles load `no-cors` and `require-corp` would
block them. After enabling, verify in order: (a) `crossOriginIsolated === true`
in the console, (b) the map still draws tiles, (c) `/video_feed` still renders,
(d) the canvas is still readable (no new "tainted" warning on
`WebcamDetect.jsx:437`). The MJPEG arrives same-origin through the proxy, so (d)
should hold — confirm it anyway.

## Tier 2 — strong, well-scoped

### 4. [ACCURACY] Per-class confidence thresholds instead of one global slider
**Effort: 1–2 h · Gain: meaningful precision gain at no recall cost**

`plastic.json` already records per-class precision and recall. The spread is
enormous: `plastic bottle` P=0.46, `plastic container` P=0.17. One global
threshold (`DETECT_CONF_FLOOR`, plus the operator slider) therefore has to be
either too strict for bottles or too loose for containers — it is currently too
loose for containers, which is where most false positives come from.

**Do:** have the training notebook emit `per_class_conf` (the F1-optimal
threshold per class from the PR curve) into `plastic.json`. In
`createPlasticDetector()` (`detector.js:161`), run the model at the *lowest*
per-class threshold and then filter each box against its own class's threshold.
Keep the operator slider as a global *offset* ("stricter ↔ looser"), not an
absolute value — that is also a better mental model for the operator.

### 5. [ACCURACY] Motion-compensate the cached tile boxes
**Effort: 4 h · Gain: fixes visibly wrong boxes during any forward flight**

`TILE_TTL = 1500` (`WebcamDetect.jsx:65`) keeps each long-range tile's boxes for
1.5 s, and one tile is refreshed per tick. At a 3 m/s cruise that is 4.5 m of
travel — the cached boxes are merged into the current frame at *stale pixel
coordinates*. On a hovering drone this is invisible; in flight it is the reason
boxes lag behind their object and `mergeBoxes` (`detector.js:358`) produces
duplicate ghosts of the same bottle.

**Do, cheapest first:**
- You already stream telemetry. Translate cached tile boxes by
  `(velocity × Δt)` projected to pixels via the FOV math already written in
  `pixelBoxToRealSize()` (`sizeEstimate.js:83`) — same pinhole model, run
  backwards. ~30 lines, no new dependency, no new compute.
- If telemetry is absent (webcam mode), estimate global translation by
  phase-correlating two 64×64 greyscale downscales of consecutive frames.
- Either way, drop a cached tile's boxes once the estimated shift exceeds ~25 %
  of the tile width rather than waiting out the TTL.

### 6. [CREDIBILITY][BUG] The 12-box cap silently undercounts the dumps you alert on
**Effort: 1 h · Gain: removes a number a reviewer can disprove**

`WebcamDetect.jsx:484` keeps only the top 12 boxes per frame:
`visible.sort((a,b)=>b.score-a.score).slice(0,12)`. The big-dump alert threshold
defaults to **8** (`alertSettings.js:21`). So the measurable range between "worth
alerting" and "saturated" is 8→12, and a raft of 40 bottles — the exact scene
Varuna exists for, and the one that will be in the demo video — reports 12.

**Do:** raise the render cap to ~64 and decouple it from counting: count every
confirmed track, cap only what gets *drawn and tracked*. Also note the sort
mutates `visible` in place; use `[...visible].sort(...)`.

### 7. [ACCURACY] Soften person suppression from "any overlap" to containment
**Effort: 1 h · Gain: recovers real detections currently deleted**

`suppressByPerson()` (`detector.js:331`) deletes any trash box overlapping a
person box **by a single pixel** — the comment says `AGGRESSIVE` deliberately.
But COCO person boxes are large and generous, so one bystander on the bank
deletes every piece of trash near them, and a bottle *held up by a person* (the
most likely webcam demo shot) never appears.

**Do:** require `overlapRatio(trash, person) > 0.6` — the trash box must be
*mostly inside* the person, which is what "the model mistook a shirt for a bag"
actually looks like. Keep the strict rule behind the existing human-detection
toggle if you want a one-tap fallback for a crowded bank.

### 8. [CREDIBILITY] Ship an evaluation harness — `npm run eval`
**Effort: 5–6 h · Gain: every future change becomes measurable instead of arguable**

There is no test or eval target in `package.json`. Today "did the detector get
better?" is answered by watching the Live tab, which cannot detect a 5 % drop and
cannot be put in a report.

**Do:** a Node script using `onnxruntime-node` that walks a held-out folder of
labelled frames, runs the exact same pre/post-processing as `detector.js`
(extract `preprocess`/`postprocess` into a shared module so the eval cannot
drift from production), and prints per-class P/R/mAP50 plus a confusion matrix.
Commit ~30 frames as a golden regression set. Then: every model swap and every
threshold change in this document gets a before/after number — including for the
report, where "we measured mAP50 0.52 on a held-out set of real river footage" is
a far stronger claim than a screenshot.

## Tier 3 — out-of-the-box differentiators

### 9. [WOW][ACCURACY] A water mask, used as a prior
**Effort: 8–10 h · Gain: large false-positive cut, plus two features that fall out for free**

`src/lib/labels.js:48` already has the concept — `filterDetections(boxes, waterZones)` and
a `river trash` class — but the live loop never passes any water zones, so the
distinction is dead code. Meanwhile every bank, rock, parked bike and bush in
frame is a false-positive opportunity that physics says can be ignored: **Varuna
can only collect what floats.**

**Do:** segment the water surface once or twice a second (a tiny
segmentation net at 128×128, or start cheaper: HSV + texture-variance
thresholding seeded by the OSM water polygon that `waterBody.js` already
fetches). Then:
- Drop detections whose centroid is off-water — a hard geometric prior,
  far more reliable than any learned confidence.
- Fill in the `river trash` vs `trash` split for real, which makes `labels.js`
  honest.
- **Report the water area actually surveyed** (m², from the FOV math in
  `sizeEstimate.js`) — which turns Varuna's output from "we saw 120 items" into
  "**0.8 items per m² over 4,200 m² surveyed**", a density. Densities are
  comparable between missions and across rivers; raw counts are not. This is the
  number a municipality or a grant committee can actually act on, and nobody
  else's demo has it.

### 10. [WOW] Operator-typed classes: zero-shot detection with no retrain
**Effort: 10–15 h · Gain: the demo moment**

Varuna's class list is frozen at six plastic types. Rivers also carry fishing
nets, thermocol idols, cloth, slippers, tyres, water hyacinth — and every one of
them needs a new dataset and a new training run today.

Open-vocabulary detection removes that: **YOLO-World** is CNN-based, ~20× faster
and ~5× smaller than Grounding DINO, exports to ONNX, and takes its class list
as *text at runtime*. An operator types "fishing net" and the next frame
detects fishing nets.

**Do:** export a YOLO-World-S ONNX and precompute the text embeddings for a
curated vocabulary at build time (so no text encoder ships in the browser —
embeddings are a small JSON). Run it as a *second opinion* on the existing
throttle the COCO verifier already uses (`cocoRunner.js`), not in the hot path.
Surface it as **"Describe what to look for"** in the Live tab.

**A second, quieter payoff:** `feedbackLearner.js` currently fingerprints objects
with a hand-built colour-histogram + edge-orientation + 8×8 thumbnail descriptor
(`describePixels`, `feedbackLearner.js:68`) — thoughtful work, but it generalises only to *the
same object seen again*. Swapping that fingerprint for a **MobileCLIP image
embedding** would let one ✖ on a sun-glint patch generalise to *all* sun glint,
not just that patch. Same UI, same RL maths (the learner is already a contextual
bandit over a feature vector — just a better vector), dramatically better
generalisation.

### 11. [WOW][CREDIBILITY] Tamper-evident detection log
**Effort: 4–5 h · Gain: turns Varuna's output into admissible evidence**

`certificate.js` and the Word report already exist, so the intent is there. Go
one step further: hash-chain each sighting in `trashLog.js` (`entry.hash =
SHA256(prevHash + canonicalJSON(entry) + photoHash)`) and print the final root
hash on the report and the certificate. Anyone can then verify that no row was
edited or deleted after the fact, without trusting Varuna or its operator.

For a system whose output might justify a fine, a cleanup contract or a grant
disbursement, "the log is verifiable" is a genuinely differentiating property —
and it is a weekend of work, not a research project.

### 12. [WOW] Predict tomorrow's accumulation zones
**Effort: 6–8 h · Gain: shifts Varuna from reporting to forecasting**

`hotspots.js` already clusters sightings with a recency weight, and
`collectionRoute.js` plans against them. That is *where trash was*. Floating
debris accumulates predictably — at meanders, bridge piers, and downwind of open
water. With the hotspot history plus river-flow direction (derivable from the
OSM waterway geometry `waterBody.js` fetches) and a wind vector, you can
propose where it will be *next*, and have the mission planner fly there first.

Even a crude version — "87 % of your sightings in the last 10 flights were within
30 m of these 3 spots; fly these first" — is a real operational recommendation
and an obvious headline for the Home dashboard.

## Latent hazards noticed in passing (no action needed yet)

- `detector.js` reuses one `Float32Array buf` per detector and hands it to
  `new ort.Tensor(...)` **without copying**, then `await session.run(...)`. The
  live loop is strictly sequential so this is safe *today* — but any future
  parallelism (running the full-frame and tile passes concurrently to use the
  idle GPU) would silently corrupt one pass's input with the other's pixels.
  Worth a comment at `detector.js:286` before someone optimises into it.
- `cocoRunner.run()` caches `lastResult` keyed on a frame token and shares the
  same `buf`; same reasoning, same caveat.
