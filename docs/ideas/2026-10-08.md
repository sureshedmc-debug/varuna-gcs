# Varuna — daily ideas, 2026-10-08

First brief. Read the live detection path (`src/lib/detector.js`,
`src/components/WebcamDetect.jsx` detect loop, `src/lib/track.js`,
`src/lib/feedbackLearner.js`, `public/models/*.json`) and cross-checked it
against current literature on riverine plastic detection.

**The headline number:** `public/models/plastic.json` reports
`map50_all: 0.2933` on its own test split. Per class: bottle 0.53, bag 0.32,
cup 0.33, container 0.12, other-plastic 0.27. Precision is 0.17–0.46. That
means **roughly one in two to one in six boxes the app draws is wrong**, and
it misses about half of real bottles. Everything downstream — counts, the
hotspot map, the weight estimate, the report, the big-dump email — inherits
that. So accuracy is the project's binding constraint right now, not UI.

Good news: the architecture is already built for a model swap. `createPlasticDetector`
reads class names, reported classes and recommended confidence from the JSON
sidecar, so a better `plastic.onnx` + `plastic.json` is a **drop-in with zero
code change**.

## Do these three first

### 1. The training data is the wrong domain — fix that and nothing else changes

`NOTICE.txt` says `plastic.onnx` was trained on TACO. TACO is ~1,500 photos of
litter **on the ground**, hand-held or on pavement, shot from eye level. Varuna
looks **down at water from altitude**. Different scale, different background,
different lighting physics (specular glare, wave texture, partial submersion).
A 0.29 mAP is what a domain gap looks like — the model is not bad, it is being
asked the wrong question.

Two open datasets close that gap:

- **RiSID** — 7,356 river-surface images from 11 sites on 7 rivers in Japan,
  recorded during **high-flow conditions**, with pixelwise annotations of
  floating macroplastic, released in **MS COCO format**. This is the closest
  public match to what Varuna's camera actually sees. Masks convert to boxes
  trivially (`cv2.boundingRect` per polygon), so it feeds a YOLO box-training
  run directly.
- **FloW-Img** — 2,000 images / 5,271 labelled floating-waste instances from an
  unmanned surface vehicle's viewpoint, i.e. low-angle, small, far debris. Good
  complement for the long-range tile pass. May need an access request (check the
  `ORCA-Uboat/FloW-Dataset` repo).

Recipe: keep TACO for class vocabulary and object diversity, add RiSID + FloW
for domain, train one model on the union, and **evaluate only on held-out river
imagery** — TACO test-split numbers are flattering and not predictive of field
performance. For reference, a 2026 study on multi-category river debris reached
mAP@0.5 = 0.70 with YOLOv10n, over twice Varuna's current figure, on this kind
of data.

While retraining, read the Nature 2026 paper on **size-tailored annotation**
first (link below). Its finding is that annotation *policy* for small debris —
grouping sub-threshold items rather than boxing each one, and matching
augmentation to object size — moved mAP more than architecture choice did. That
is a free lever before you spend GPU hours.

Effort: a Colab afternoon, same as last time. Expected gain: the largest
available by a wide margin.

### 2. Count tracks, not frames — a 15-line change that kills most false positives

In the detect loop, `recordTrashCount(counted.length)` and `recordTrashSighting`
both act on **the current frame's** boxes. So a box that appears for a single
frame — which is exactly what sun glint on a wave crest, a foam streak, or a
flicker of chop looks like to the detector — counts as a real item, geotags a
hotspot, and can trip the big-dump email.

Real floating debris persists across many frames. Transient artifacts do not.
`BoxTracker` already matches boxes by IoU and keeps them for `maxAgeMs = 700`,
so the information needed is already there and just isn't used:

- in `track.js`, add `hits` to each track (`t.hits++` on match, `hits: 1` on
  create) and emit it in the returned object;
- in the loop, define `counted` as `b.rl === 'show' && b.hits >= 3` instead of
  `b.rl === 'show'`;
- keep drawing boxes at `hits >= 1` so the operator still sees instant feedback
  — only *counting*, *logging* and *alerting* wait for confirmation.

This costs no inference and no model change, and it raises precision on exactly
the failure mode that water surfaces generate most of. Of everything in this
brief, it is the best ratio of impact to effort.

### 3. Per-class confidence thresholds, not one slider for five classes

`plastic.json` already shows the five reported classes differ in precision by
nearly 3× (bottle 0.46, container 0.17). But the whole pipeline applies one
number: `Math.max(DETECT_CONF_FLOOR, confRef.current)` for every class, and the
tile pass scales that one number by `TILE_CONF_FACTOR`.

The result is unavoidable: any slider position good for bottles floods the
screen with bad `container` and `other plastic` boxes, and any position that
silences those throws away half the bottles.

Fix in the sidecar, where the design already points: add

```json
"class_conf": { "0": 0.22, "1": 0.30, "2": 0.30, "3": 0.45, "4": 0.38 }
```

and have `createPlasticDetector`'s filter compare each box against
`class_conf[b.cls]` (falling back to the global threshold) instead of a single
value. Calibrate each entry on the test split for a common target precision
(~0.5) rather than by eye. The operator's slider then becomes a global
sensitivity *bias* on top of per-class calibration, which is what it should
have been.

Effort: an hour of code, an hour of calibration. No retrain needed — this
extracts accuracy from the model you already have.

## Worth doing next

### 4. Three detectors are loaded; the most useful verifier is switched off

`NOTICE.txt` describes `coco-yolo.onnx` as a verifier whose `bottle` class
"identifies plastic bottles specifically" and whose confident hits on other real
objects suppress overlapping trash boxes. That is a good design — **but it is
not what the code does.** The loop only calls `detectPersons`, which reads COCO
class 0 and nothing else. `src/lib/cocoDetector.js` is never imported from
anywhere; likewise `src/lib/labels.js` (`filterDetections`, `normalizeLabel`,
and its whole `isWater` branch) has zero call sites. The model is already
loaded, already running every frame, already paid for in latency — and 79 of its
80 classes are discarded.

Two free signals sitting in that tensor:

- **Positive:** a trash box overlapping a confident COCO `bottle` (class 39) is
  near-certainly a real plastic bottle. Use it to boost score and to pin the
  class, which the single-class `plastic_detection` model cannot do at all.
- **Negative:** a confident COCO hit on `bird`, `boat`, `dog`, `car`, `umbrella`
  overlapping a trash box means the trash box is that object. Suppress it the
  same way `suppressByPerson` already does for people.

Pass the same `frame` token that `detectPersons` uses and this costs **zero
extra inference** — `cocoRunner` already caches one pass per frame token.

### 5. Drift coherence — the physical signal nothing is using yet

Floating debris moves with the current: all real items in frame drift in a
consistent direction at a consistent speed. Glint moves with the sun and the
camera; wave crests appear and vanish in place. So a track whose velocity
disagrees sharply with the median velocity of all tracks is probably not debris.

`feedbackLearner` is already set up to take this: `featureDim()` is
parameterized and `EXTRA_FEATURES = 8` is just a constant. Store previous
positions in `BoxTracker`, derive per-track velocity, and add two features —
speed, and cosine agreement with the median drift vector. The contextual bandit
then learns how much to trust them from the operator's ✔/✖ answers, which is
better than hard-coding a threshold.

Bonus: a median drift vector *is* the surface current estimate. That is a
genuinely useful readout for the operator and it feeds idea 9.

### 6. Seed the learner with a glint prior instead of starting from "show everything"

`PRIOR_BIAS = 1.5` means the learner shows everything until taught otherwise —
sensible as a default, but it means every operator re-teaches the same lesson
about sun glare from scratch on every device.

`describePixels` already computes `bright`, `sat` and `contrast`, and glint has
an unmistakable signature: very high brightness, very low saturation, low
internal contrast. Ship non-zero starting weights on those three features
(equivalent to a handful of synthetic ✖ answers) so a fresh install already
routes blown-out highlights to `explore` rather than counting them. The operator
can still overrule it — the rules layer already wins over the learner.

### 7. Flip-TTA on the tile pass, inside the budget logic that already exists

The loop already measures its own cost (`emaRef`) and already escalates the tile
grid from 2×2 to 3×3 when `ema <= BUDGET_MS * 0.4`. In that same headroom
branch, run the *active tile only* a second time horizontally flipped, unflip
the boxes, and merge through the `mergeBoxes` you already have. Test-time
augmentation reliably buys a little small-object recall, and this spends it only
when the machine has spare time — on a loaded machine the branch never fires and
nothing changes.

### 8. Use the OSM water polygon you already fetch to reject off-water detections

`waterBody.js` already pulls real water-body outlines from OpenStreetMap, and
the drone already reports lat/lng/alt. `sizeEstimate.js` already converts
altitude + FOV into the ground footprint of the frame. Put those together and
you can test whether a detection sits **inside the river** or on the bank.

During a river-cleanup mission, a box on the bank is either irrelevant (you
cannot collect it) or a false positive. Either way it should not enter the count
that drives the collection route. This is the `isWater` idea that `labels.js`
sketched and never wired up — except grounded in real geometry instead of
hand-passed rectangles. Needs heading to be exact; without heading, a
centre-weighted "is the drone over water at all" test is still worth having.

## The out-of-the-box play

### 9. Make Varuna report **flux**, and it stops being a demo

Right now Varuna answers "how much trash is in this frame". Researchers,
municipalities and river authorities all ask a different question: **how much
plastic passes this point per hour, and how many kg per day.** That is the unit
the entire field reports in, and it is the unit that makes a number citable in a
budget request or a policy document.

Varuna is unusually close to being able to answer it. It already has item counts
with timestamps, GPS, altitude, the ground-width conversion in
`pixelBoxToRealSize`, and per-class average item mass in `DEFAULT_AVG_WEIGHT_G`
— which is exactly the method the literature uses (items/hour × mean mass per
item → kg/hour → kg/day). What is missing is small:

- **An observation window.** The standard protocol counts for a fixed 2–30
  minutes and extrapolates linearly. Add a "Survey" mode: pick a duration, hover
  on station, get a count.
- **Width coverage.** The frame covers only part of the river. Ground width is
  already computable from altitude and FOV; river width is already available
  from the OSM polygon in `waterBody.js`. Their ratio is the coverage fraction,
  and the protocol normalizes by it. Published surveys cover 20–90 % of width
  and say so — Varuna can compute it automatically, which a human observer on a
  bridge cannot.
- **Honest uncertainty.** Report a range, not a point. State plainly that this
  is the floating, visible fraction only.

Output: *"Hussain Sagar, north inlet — 1,240 items/h (±35 %), ~28 kg/h,
~670 kg/day, 41 % of channel width observed, 12-minute window, 2026-10-08."*
That is a line a city engineer can act on and a journal can print, and
`reportDoc.js` already knows how to render a report around it.

### 10. Count items **crossing a line**, not items in view

Flux needs items crossing a transect, and that also fixes a double-counting bug
that will bite in opposite directions depending on how the drone is flown:

- **Hovering** over a flowing river, new items drift through continuously —
  counting items in frame undercounts badly.
- **Flying along** the river, the same items stay in frame — counting items in
  frame overcounts badly.

`trashLog.js` merges sightings within ~5 m geographically, which helps the second
case and actively hurts the first. A transect counter solves both: draw a virtual
line across the channel, and count a track exactly once, when its centre crosses
it. The tracker already gives stable per-track ids with the persistence needed to
detect a crossing, and idea 5's drift vector tells you which way the river flows
so the line can be placed perpendicular to it automatically.

This is also what makes idea 2 (`hits >= 3`) and idea 9 compose: confirmed
tracks, counted once each, over a known window, normalized by known width. That
chain is the difference between a detection toy and an instrument.
